Computer-use agent · system design

Inside os-agent

An agent that drives a real macOS desktop by looking at screenshots. It is not trying to be the most accurate one. It is trying to be the same accuracy, five to ten times faster — and to prove it with numbers that someone else could reproduce.

A0 permissions · passed A1 seams & guardrails · passed A2 perception · in progress A3–A8 · ahead

The premise

One number decides whether this project works

Published computer-use agents are accurate and unusably slow — tens of minutes for tasks a person does in two. The causes are structural rather than about model quality: several model calls per step, and a context that grows until late steps cost three times what early ones did.

So the target is not “be smart.” It is LLM calls per step = 1.0. A step costing one 2.5 s vision call makes a 15-step task about 40 s of model time. The same step costing four calls — plan, ground, verify, reflect — makes it 160 s before context growth multiplies it. Every architectural decision below is downstream of holding that ratio at one.

The trick

Verification without a second model call

Most agents ask a model “did that work?” That is the second call, and it is the one that quietly doubles the bill. The alternative costs nothing: the planner already knows what it expects to happen, so it says so in the same response.

FieldWhat it buys
actionthe thing to do
expecta machine-checkable postcondition — “an element named ‘Save’ disappears”

new_factat most one durable discovery, to keep memory bounded

Verification becomes a string comparison. The outcome is deliberately not a boolean — it is success, no_change, error, or ambiguous. Only ambiguous escalates to a model, so ambiguous rate is tracked as a headline metric: it is literally the count of calls we failed to avoid.

Grounding

The model sees a picture. How does it say where to click?

There are only three answers, and the choice sets the architecture. This is the single most consequential design decision in the system.

Perception

Filtering is the decision, not the tree walk

The accessibility tree is the desktop's equivalent of a DOM: every control's role, name and geometry, published by the OS so screen readers can work. Reading it is mechanical. Deciding which nodes deserve a number is the part that determines whether the agent functions, and it is squeezed from both sides.

Structure

Three seams, and nothing else gets an interface

Every abstraction exists because we cross that boundary ourselves — swapping a backend to test, swapping a model to compare, replacing the loop entirely in Phase B. Nothing was abstracted for a hypothetical future user.

The budget

Where one step actually goes

Perception runs concurrently — the screen capture and the accessibility walk have no dependency on each other, which is the entire reason the environment layer is async while the adapter beneath it is not.

perception 77 ms (measured, concurrent) model call ~1,500 ms (estimated — not yet measured) settle wait 500 ms (blind sleep, Phase B target) verify ~25 ms

Two things are visible here that matter. The model is roughly seventy percent of a step, so calls-per-step dominates everything else. And the second largest item is not clever at all — it is a blind half-second sleep waiting for the interface to settle, which Phase B replaces with polling until the screen stops changing.

The honesty rule

Amber means estimated, teal means measured on this machine. Every guess in this system gets replaced by a measurement and the spec gets corrected — including when the measurement is embarrassing. Two already were.

The path

Eight gates, each one closed before the next opens

The ordering is not bureaucracy. Routing bugs are trivial to find when the nodes only print and miserable to find when a real desktop and a real model are also in the picture — so the graph gets tested against recorded observations before it is allowed near either.

Why A6 is the one that matters

Everything before it builds a thing. A6 is where the thing acquires a number. After that the tasks are frozen — tuning the agent is the project, tuning the benchmark is fraud — and Phase B can begin, where each optimization is measured as a delta against a baseline that can no longer move.
